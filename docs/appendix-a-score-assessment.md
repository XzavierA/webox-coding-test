# 附录 A 评分预评估

## 1. 结论

在本方案全部正确实现并通过验收的前提下：

- Tier 1 + Tier 2 目标为 **50 / 50**，超过 45 分功能门槛。
- Tier 3 实现库存实时扣减和经营看板，不实现 AI。附录只公布 Tier 3 总计 `+10`，没有公布三个子项权重，因此准确加分只能表示为 `库存权重 + 看板权重`。若按常见拆分估计，约为 **+6～+8 / 10**，该区间不是正式评分规则。
- 前端岗位 P6+ 设计覆盖 **20 / 20**。
- 后端岗位 P6+ 设计覆盖 **20 / 20**。
- 仅就附录 A 已公布的“功能 60 + P6+ 20”口径，完整实现后的预期目标约为 **76～78 / 80**。若三个 Tier 3 功能等权，则约为 `50 + 6.67 + 20 = 76.67 / 80`。

这不是当前实得分。当前仓库只有设计文档，没有运行代码、测试和端到端证据；按严格面试评分，功能与 P6+ 均暂时不可计分。

### 并发安全满分闸门

必须同时满足：

1. Redis Lua 在同一原子操作中完成全部库存检查、扣减、reservation 记录和 `XADD`。
2. Redis reservation 不代表成功；只有 MySQL 事务确认后才返回/展示成功。
3. Stream 至少一次投递通过 MySQL 唯一 reservation/idempotency 记录去重。
4. MySQL 仍执行 `remaining_stock >= requested` 条件更新，不信任 Redis 快照。
5. 终态失败执行幂等补偿；崩溃重投不会重复扣减或恢复。
6. 定时对账能发现并修复 Redis、MySQL、movement ledger 的差异。

如果实现成“Redis 扣完立即返回成功，随后尽力异步写 MySQL”，则存在 Redis 数据丢失、消费者失败和双写不一致。该实现不能按 4 / 4 评价，并可能触发库存、实时同步、看板真实数据等 Tier 3 项的级联归零。

## 5. 认证修改的评分影响

短 JWT + 长 refresh cookie 不直接增加独立分数，但能强化权限项和安全质量。满分实现需满足：

- access JWT 仅存在内存，通过 `Authorization` 发送；
- refresh token 只在 `HttpOnly + Secure + SameSite + Path` cookie 中；
- refresh 每次旋转，旧 token 重用会撤销整个 family；
- JWT 固定算法、校验 issuer/audience/expiry，并支持 key ID 轮换；
- 统一 Filter 只负责认证并建立 `AuthenticatedActor`，URI/方法/资源归属分别完成授权；
- 后续应用上下文显式接收 `CurrentActor`，不信任客户端传入 user ID/role。

## 6. 当前主要扣分风险

1. Redis-first 库存链路比同步 MySQL 更复杂，若没有崩溃窗口和对账测试，设计优势无法转化为分数。
2. Tier 3 AI 明确不实现，因此不可能获得 Tier 3 满额 10 分。
3. 后台状态机必须使用条件更新和版本号；仅靠前端隐藏按钮无法证明状态安全。
4. 完整 AI 对话原始导出是交付铁律，缺失会影响最终评级，即使功能分较高。
